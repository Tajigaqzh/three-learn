# 手机 H5 文章富文本编辑器技术选型

## 1. 文档目的

本文对 TinyMCE、wangEditor、Quill 和 Tiptap 进行技术选型，目标场景是：

- 运营人员主要在 PC 发布后台编辑文章；
- 支持从 Microsoft Word 粘贴文字、颜色、字号、列表、表格和图片；
- 最终发布为类似微信公众号文章的手机 H5 页面；
- 发布页只负责展示，不在手机端加载完整编辑器；
- 内容需要安全、可清洗、可再次编辑，并适配不同尺寸的手机屏幕。

## 2. 项目约束

当前项目的相关技术条件：

| 项目       | 当前情况               | 对选型的影响                                       |
| ---------- | ---------------------- | -------------------------------------------------- |
| 前端框架   | React 17               | 需要提供 React 集成或能以受控组件方式接入          |
| 构建工具   | Rsbuild                | 编辑器及插件需要能够被现有构建链处理               |
| 浏览器基线 | Chrome 67              | 候选版本必须做兼容验证，必要时固定旧版本或补充转译 |
| HTML 安全  | 已使用 DOMPurify 2.5.8 | 可以复用，但发布接口后端仍需再次过滤               |
| 发布载体   | 手机 H5                | 输出不能携带 Word 页面宽度、页边距等桌面排版属性   |
| 主要输入源 | Word 和后台手工编辑    | Word 粘贴质量是首要指标                            |

> Chrome 67 是明显的版本约束。各编辑器最新版通常面向现代浏览器，不能只根据官网“支持 Chrome”直接判断兼容；必须使用拟采用的确切版本进行构建和真机验证。

## 3. 核心需求

### 3.1 必须满足

1. 支持段落、标题、粗体、斜体、颜色、字号、链接、列表、引用、图片和表格。
2. 从 Word 粘贴后，能够清除 `mso-*`、`MsoNormal`、Office XML 等冗余内容。
3. 粘贴图片能够上传到业务文件服务，并将临时地址替换为正式 HTTPS 地址。
4. 输出内容可以在 320px 至 430px 宽的手机页面中正常展示。
5. 防止 XSS，不允许事件属性、脚本、危险 URL 和不受控的嵌入内容进入发布结果。
6. 已发布文章可以重新进入编辑器继续编辑。

### 3.2 建议满足

1. 支持撤销、重做、查找替换、字数统计和草稿自动保存。
2. 支持图片替代文本、链接安全属性和基础无障碍语义。
3. 支持粘贴前后预览，以及 375px 手机宽度预览。
4. 能限制字号、颜色、图片尺寸等，避免运营内容破坏页面布局。

### 3.3 当前不作为首期目标

- Notion 式块编辑；
- 多人实时协同；
- 批注和修订模式；
- Word 文档像素级还原；
- 手机端完成复杂文章创作。

## 4. 候选方案对比

| 产品定位     | 完整的成品富文本编辑器             | 面向国内项目的成品编辑器              | 以 Delta 为核心的轻量编辑器    | 基于 ProseMirror 的无头编辑器框架 |
| 默认工具栏   | 完整                               | 完整                                  | 基础                           | 基本需要自行开发                  |

| 表格能力     | 成熟                               | 满足基础场景                          | 原生能力相对有限               | 扩展能力强                        |
| 图片处理     | 插件和事件完整                     | 常规上传容易接入                      | 需要围绕 Blot/模块扩展         | 可以完全定制节点和上传流程        |

| 内容约束能力 | 较强                               | 中等                                  | Delta 格式受控                 | 最强，可严格定义 Schema           |
| 扩展上限     | 高                                 | 中等                                  | 中等                           | 最高                              |
| 初始开发成本 | 低                                 | 低                                    | 中                             | 高                                |
| 中文资料     | 一般                               | 丰富                                  | 较多                           | 较多                              |
| 协同编辑     | 有成熟方案，部分为商业能力         | 不是核心优势                          | 可集成第三方协同方案           | Yjs/Hocuspocus 生态成熟           |
| 授权注意事项 | 核心与商业插件需分别确认授权       | 以采用版本许可证为准                  | 以采用版本许可证为准           | 核心与商业扩展需分别确认授权      |

### 4.1 TinyMCE

优势：

- 成品能力完整，工具栏、表格、图片和粘贴链路成熟；
- 对 Word 生成的 HTML 和 Office 私有样式有较多处理经验；
- 可以较快交付传统 CMS/公众号式文章编辑功能；
- 插件和事件接口较完整，便于增加图片上传、内容过滤和预览。

风险：

- PowerPaste 等专业 Word 粘贴能力可能需要商业授权；
- 如果不使用专业粘贴插件，复杂 Word 表格和图片仍需补充清洗逻辑；
- 深度改变内容模型和编辑交互不如 Tiptap 灵活；
- 需要确认拟采用版本对 Chrome 67 和 React 17 的实际兼容性。

适用判断：最符合当前“Word 粘贴优先、快速完成文章发布”的需求。

### 4.2 wangEditor

优势：

- 中文文档和国内使用经验丰富；
- 常规文章编辑、图片上传和 React 接入成本较低；
- 默认界面符合国内管理后台的使用习惯；
- 不追求复杂 Word 还原时，性价比较高。

风险：

- 复杂 Word 表格、Office 私有标记和特殊图片需要自行处理；
- 插件生态、复杂文档能力和长期扩展上限弱于 TinyMCE/Tiptap；
- 需要核实所选版本的维护状态、依赖版本和 Chrome 67 兼容性。

适用判断：可作为不采购商业粘贴能力时的备选，但需要接受部分格式损失并投入自定义清洗。

### 4.3 Quill

优势：

- Delta 数据模型明确，内容存储和变更表达稳定；
- 基础编辑场景成熟，适合评论、消息和格式受控的短内容；
- 内容不会直接保留任意 Word HTML，数据相对规整。

风险：

- Word HTML 需要通过 Clipboard 模块转换为 Delta，未识别格式会丢失；
- 表格、复杂嵌套排版和 Word 高保真粘贴不是主要优势；
- 自定义格式需要理解 Delta、Parchment 和 Blot；
- 本项目需要的是完整长文章发布，其优势与核心需求不完全匹配。

适用判断：不建议作为本场景首选。

### 4.4 Tiptap

优势：

- 基于 ProseMirror，Schema、节点、标记和命令的定制能力最强；
- 可以同时保存结构化 JSON 和生成 HTML；
- 适合后续建设块编辑、协同、批注、AI 改写等产品能力；
- 能严格限制内容结构，长期可维护性较好。

风险：

- 它是编辑器框架而不是完整成品，工具栏、弹窗、上传和大量交互需要自行开发；
- Word 粘贴需要自行设计 DOM 到 Schema 的映射和清洗策略；
- 学习成本和首期开发成本最高；
- 部分高级扩展或服务需要单独评估授权。

适用判断：如果未来目标升级为自研内容平台，可以重新评估；当前公众号式文章发布属于投入过度。

## 5. 加权评分

采用 1 至 5 分制，5 分最好。评分针对当前需求，不代表编辑器的通用优劣。

| 评价项             |     权重 |  TinyMCE | wangEditor |    Quill |   Tiptap |
| ------------------ | -------: | -------: | ---------: | -------: | -------: |
| Word 粘贴质量      |      30% |        5 |          3 |        2 |        3 |
| 手机 H5 输出可控性 |      20% |        4 |          4 |        4 |        5 |
| 首期交付成本       |      15% |        5 |          4 |        4 |        2 |
| 扩展能力           |      15% |        4 |          3 |        3 |        5 |
| 表格与媒体能力     |      10% |        5 |          3 |        2 |        4 |
| 生态与维护能力     |       5% |        5 |          3 |        4 |        5 |
| 授权成本可控性     |       5% |        2 |          5 |        5 |        4 |
| **加权总分**       | **100%** | **4.50** |   **3.45** | **3.10** | **3.80** |

说明：TinyMCE 的 Word 粘贴评分按启用专业粘贴能力计算。如果只使用免费基础能力，需要通过 PoC 重新评估该项，得分可能下降。

## 6. 选型结论

### 6.1 推荐方案

选择 **TinyMCE 作为 PC 发布后台编辑器**，手机 H5 使用独立、只读的文章渲染组件。

推荐理由：

1. Word 粘贴是当前权重最高的需求，TinyMCE 的现成能力最匹配；
2. 当前目标是传统文章发布，不需要承担 Tiptap 的框架建设成本；
3. 编辑器只存在于发布后台，不会增加普通 H5 读者的首屏包体；
4. 输出 HTML 可以接入现有 DOMPurify 和统一移动端样式。

### 6.2 降级方案

如果商业授权预算无法通过，选择 **wangEditor + 自定义 Word HTML 清洗器**。该方案需要明确接受：

- 复杂 Word 表格可能降级；
- 特殊字体、文本框、SmartArt 和分页信息不保证保留；
- 图片提取和上传需要自行开发；
- 需要增加更多 Word 样本回归测试。

### 6.3 暂不选择

- Quill：Word 和长文章能力与本次需求不匹配；
- Tiptap：扩展上限高，但首期建设成本明显超出当前需求。

## 7. 推荐技术架构

```text
Word / 手工输入
       ↓
PC 发布后台 TinyMCE
       ↓
粘贴预处理：选择 text/html，识别 Word 来源
       ↓
内容标准化：清理 Office 节点、mso-*、固定页面尺寸
       ↓
图片处理：提取临时图片 → 上传文件服务 → 替换正式 URL
       ↓
安全过滤：前端 DOMPurify + 后端白名单过滤
       ↓
保存编辑态 HTML 和发布态 HTML
       ↓
手机 H5 文章组件按统一 CSS 只读渲染
```

### 7.1 数据存储建议

建议至少保存：

| 字段             | 用途                              |
| ---------------- | --------------------------------- |
| `sourceHtml`     | 清洗后的可编辑 HTML，用于重新编辑 |
| `publishedHtml`  | 经过严格白名单过滤的发布 HTML     |
| `plainText`      | 搜索、摘要生成和字数统计          |
| `contentVersion` | 内容转换规则升级和数据迁移        |

不要保存并直接发布未经处理的 Word 原始 HTML。样本 `word.html` 中真正正文只有一个段落和 6 个 `span`，但同时携带了大量 Office 元数据和潜在样式。

### 7.2 HTML 白名单建议

首期允许的标签可以限制为：

```text
p, br, h1-h6, strong, em, u, s, blockquote,
ul, ol, li, a, span, img, figure, figcaption,
table, thead, tbody, tr, th, td, pre, code
```

建议允许的样式属性：

```text
color, background-color, font-size, font-weight,
font-style, text-decoration, text-align, line-height
```

应删除：

- `script`、`iframe`、`object`、`embed`；
- 所有 `on*` 事件属性；
- `javascript:` 等危险 URL；
- Word 的 `xml`、`w:*`、`o:*` 节点；
- `mso-*`、`MsoNormal`、`@page` 和固定纸张尺寸；
- `file:`、本地磁盘地址和未完成上传的 `blob:` URL；
- 固定宽度、负边距、绝对定位和高 `z-index`。

### 7.3 移动端渲染原则

- 正文字号默认 17px，行高建议 1.7 至 1.8；
- 图片和视频使用 `max-width: 100%; height: auto`；
- 表格放在可横向滚动容器中，不能撑破页面；
- 长链接和长英文使用 `overflow-wrap: anywhere`；
- Word 的 `pt` 字号在清洗阶段转换并限制范围，例如 `10.5pt = 14px`、`18pt = 24px`；
- H5 只加载文章渲染 CSS，不加载编辑器脚本和样式。

## 8. 安全与质量要求

1. 前端过滤只用于即时反馈，不能替代后端安全过滤。
2. 后端以标签、属性、协议三层白名单处理发布内容。
3. 图片必须上传到受控域名，验证 MIME、扩展名、大小和分辨率。
4. 外部链接默认增加 `rel="noopener noreferrer"`，并根据业务决定是否允许跳转。
5. 清洗逻辑必须基于 DOM 解析，不能仅依赖正则表达式处理 HTML。
6. 编辑预览与正式 H5 使用同一套文章样式，减少发布前后差异。

## 9. PoC 验证计划

正式采购或开发前，用相同测试集验证 TinyMCE 和 wangEditor，控制 PoC 在 1 至 2 个工作日内完成。

测试样本至少包括：

1. 普通段落、中文字体、颜色和多级字号；
2. 有序列表、无序列表和多级列表；
3. 合并单元格、背景色和边框不同的 Word 表格；
4. Word 内嵌 PNG、JPEG、截图和复制的图表；
5. 超长文章、50 张图片和大表格；
6. 外部链接、危险标签和事件属性；
7. 当前 `word.html` 这类包含 Office 元数据及异常编码的内容；
8. Chrome 67、当前主流 Chrome，以及目标 Android/iOS WebView 的展示结果。

验收标准：

| 指标           | 验收要求                                          |
| -------------- | ------------------------------------------------- |
| 普通文字与段落 | 内容完整，顺序不变                                |
| 颜色与字号     | 常用格式保留，字号落入允许范围                    |
| 列表           | 层级和序号正确                                    |
| 表格           | 内容不丢失，手机端不撑破页面                      |
| 图片           | 全部转为正式 HTTPS 地址，无本地路径和 `blob:`     |
| HTML 体积      | Office 冗余内容被清除，不能原样保存完整 Word HTML |
| 安全           | XSS 测试样本不能执行                              |
| 兼容性         | 编辑后台目标浏览器可用，H5 目标 WebView 展示一致  |

## 10. 决策与后续动作

当前决策：**优先使用 TinyMCE，wangEditor 作为无商业授权预算时的备选。**

实施前需要完成：

1. 确认编辑后台是否必须支持 Chrome 67；
2. 确认 TinyMCE 具体版本、插件清单和商业授权费用；
3. 使用真实 Word 文档完成 TinyMCE/wangEditor PoC；
4. 确认图片上传接口、内容保存接口和后端 HTML 白名单；
5. 确认 PoC 结果后锁定版本，并记录浏览器兼容矩阵。

如果 TinyMCE 在授权、Chrome 67 或真实 Word 样本上不能通过验收，则按降级方案切换到 wangEditor，并将 Word 清洗和图片提取列为独立开发任务。
